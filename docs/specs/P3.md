## 0. 목표와 완료 그림

`npm run seed && npm run build && npm start` 후 `http://localhost:7777/trainer`:
1. "세션 시작" (기본 20문제, 차트셋 전부, 카테고리 전부) → 첫 스팟: `HU push/fold 10bb · SB · root · 팟 1.5bb`, 히어로 카드 **`A♠ 7♦`** 두 장, 격자는 **뷰어와 같은 컴포넌트**인데 전략 레이어가 없고 `A7o` 셀만 강조. 답 버튼 = 그 노드의 `actions` (`F` / `A`).
2. `A` 클릭 → 같은 화면에서 마스크가 벗겨진다: 격자에 전략 레이어, 우측에 채점 박스 `Perfect · EV loss 0.00bb · 당신 A (100%) · 최선 A +1.42bb`, 액션표 `F 0% 0.00 / A 100% +1.42`. "다음" → 다음 스팟.
3. 혼합 스팟(예: 8bb SB `K2o` 가 `A` 63%)에서 37% 쪽 `F` 를 골라도 EV loss 가 0.05bb 미만이면 **Perfect** 다. 화면 어디에도 "정답/오답" 이란 말이 없다 (D8).
4. 20문제 끝 → 세션 리포트: 총 EV loss, bb/100, verdict 분포, 카테고리별(`open` / `vs_jam`) 분해. "리포트 30d" 탭에 누적 + **리크** (`vs_jam · 평균 0.31bb · 47회`).
5. 다음 날 같은 스팟이 SRS 에 의해 다시 나온다. 3회 이상 Blunder 인 스팟은 leech 큐로 세션 앞에 강제 배치.

**만들지 않는 것**: 포스트플랍 스팟(P6), SRS 파라미터 편집 UI, 다중 사용자, 핸드히스토리 임포트, 외부 기록 임포트/익스포트, 모바일 레이아웃, 차트 편집, 6-max 시드 (P3 는 P2 시드 6개 + 임포트된 `ggto-json` 이면 무엇이든).

**시작 조건**: 없음 (P2 시드에 EV 가 있으므로 `graded_by:'ev'` 경로를 실제 데이터로 시작한다). **단 10.0 (정확 에퀴티 표) 을 P3 의 첫 작업으로 한다** — 시드 `content_hash` 가 바뀌는 일은 기록이 쌓이기 전에 끝내야 한다.

## 3. 도메인 정의 (전부 고정)

### 3.1 스팟과 스팟 키
```ts
export interface Spot {
  key: string;            // 3.1 형식
  contentHash: string;    // chart_set.content_hash (영구 식별자)
  chartSetId: number;     // API 핸들 (세션 중 유효). 기록에는 저장하지 않는다
  seq: string;            // 노드 키 (루트 '')
  heroPos: string;        // 노드 hero_pos
  potBb: number;
  actions: readonly string[];   // 노드 actions (답 후보)
  combo: ComboIndex;      // 히어로 콤보 (1326)
  category: Category;     // 3.2
  gradedBy: 'ev' | 'frequency';   // = chart_set.has_ev ? 'ev' : 'frequency' (D8)
}
```
**스팟 키** = `pf:<content_hash>:<seq>:<combo>` — `combo` 는 P2 5.1 의 1326 키 규약 `formatCard(hi)+formatCard(lo)` (`AsKh`, hi>lo). 루트는 `pf:<hash>::AsKh` (빈 seq). `parseSpotKey`/`formatSpotKey` 는 왕복 항등이어야 하고 (테스트), 접두 `pf:` 외·해시 64hex 아님·콤보 비정규(`KhAs`)·seq 파싱 실패는 `SpotKeyError`. `ps:` 접두는 P6 포스트플랍용으로 예약 (지금은 거부). 이 문자열이 `attempt.spot_key`·`srs_state.spot_key`·API 필드다.

### 3.2 카테고리 (프리플랍 v1, `categoryOf(config, seq)`)
상태 기계로만 정한다 (`preflopState(config, parseActionSequence(seq)[0] ?? [])`). `r` = `actionsTaken` 중 `R*`·`A` 의 개수, `limped` = `r === 0` 이고 `C` 가 하나 이상, `facingJam` = 어떤 포지션이 `allIn` 이고 히어로가 `C` 하면 자기도 올인이 되는 상태 — **`allIn` 이 비어 있지 않고 `toAct` 가 있고 `currentBet ≥ stack`** (R2: `currentBet` 은 "to" 금액이라 히어로 투입분이 이미 들어 있다. R1 의 `stack − contributions[hero]` 는 이중 차감이었고, 균등 스택 프리플랍에서 `allIn` 이 비어 있지 않으면 `currentBet = stack` 이므로 두 식은 도달 가능한 상태 전부에서 동치다 — `test/category.test.ts` 가 시드 전 노드에서 고정한다). 상태 기계 값으로만 판정하고 손으로 다시 계산하지 않는다.

| 조건 | 카테고리 |
|---|---|
| `r === 0 && !limped` | `open` |
| `r === 0 && limped` | `vs_limp` |
| `r ≥ 1 && facingJam` | `vs_jam` |
| `r === 1` | `vs_open` |
| `r === 2` | `vs_3bet` |
| `r ≥ 3` | `vs_4bet_plus` |

P2 시드에서는 루트 = `open`, `A` = `vs_jam` 뿐이다. 6-max 차트가 들어오면 나머지가 산다. `Category` 는 이 6개 문자열의 union 타입이고 DB CHECK 에도 같은 목록.

### 3.3 채점 (D8 — 빈도 일치 채점 금지)
입력: 노드 `strategy[a][c]`, `ev[a][c] | null`, 히어로 콤보 `c`, 고른 액션 `chosen ∈ actions`.

**`gradedBy === 'ev'`** (`chart_set.has_ev = 1`. P2 3.3 이 "노드 단위 전부 아니면 전무" 를 보장하므로 차트셋 단위로 정해진다):
```
best      = max_a ev[a][c]                 (a 는 노드 actions 전부 — 빈도 0 인 액션도 후보)
evLossBb  = max(0, best − ev[chosen][c])   (f32 잔차로 −1e-7 이 나오면 0)
verdict   = evLossBb < 0.05 ? 'Perfect' : < 0.3 ? 'Minor' : < 1.0 ? 'Mistake' : 'Blunder'
```
EV 단위는 P2 3.3 (`stack_delta_from_node`, bb). 폴드 EV 0 과 직접 비교 가능. **임계 0.05 는 D7 (f32) 과 P2 7.1 의 MC 노이즈(~1e-3bb) 위에 있다.**

**`gradedBy === 'frequency'`** (`has_ev = 0` 인 외부 차트 폴백):
```
chosenFreq = strategy[chosen][c]
verdict    = chosenFreq ≥ 0.01 ? 'InStrategy' : 'OffStrategy'
evLossBb   = null
```
두 체계의 verdict 는 **서로 다른 문자열**이고 리포트에서 절대 합산되지 않는다 (7절). UI 는 `frequency` 스팟에 "빈도 채점 (EV 없음)" 배지를 붙인다.

`Grade` 반환:
```ts
export interface Grade {
  gradedBy: 'ev' | 'frequency';
  verdict: 'Perfect' | 'Minor' | 'Mistake' | 'Blunder' | 'InStrategy' | 'OffStrategy';
  evLossBb: number | null;
  chosenAction: string; chosenFreq: number;
  bestAction: string;          // argmax ev (ev 없으면 argmax strategy)
  bestEvBb: number | null;
  mixed: boolean;              // 3.4
  actions: { action: string; freq: number; evBb: number | null }[];   // 히어로 콤보의 행
}
```

### 3.4 혼합 (P2 R1 MINOR 5)
콤보 `c` 에서 `mixed(c) := |{ a : strategy[a][c] ≥ 0.01 }| ≥ 2`. 2액션 노드에서는 정확히 "min 빈도 ≥ 0.01" 이고, 3액션 이상에서는 그 일반화다 (`[0.6, 0.4, 0]` 은 혼합, `[0.995, 0.005]` 는 순수 — CFR+ 잔차 0.999813 이 혼합으로 보이지 않게). 노드의 **혼합 질량** `mixedMass = Σ_c reach[c]·mixed(c) / Σ_c reach[c]` 는 5절 난이도 가중치.

### 3.5 균형 일관성 (실데이터 성질 게이트)
P2 시드 6개 × 모든 노드 × 1326 × `strategy[a][c] ≥ 0.01` 인 모든 `(a, c)` 에 대해 `max_a' ev[a'][c] − ev[a][c] < 0.01bb`. 균형에서 실제로 플레이되는 액션은 최선과 무차별이어야 하며, 이것이 깨지면 차트나 채점기 중 하나가 틀린 것이다. **이 테스트가 3.3 채점기의 1차 정확성 근거다.**

PRAGMA foreign_keys = ON;

## 5. 샘플러 (`nextSpot(session)`)

### 5.1 후보 풀
필터에 맞는 차트셋의 **비터미널 노드 전부** (`listNodes` → `preflopState` 로 터미널 제외 — P2 6.2-3 이 이미 보장하지만 다시 확인). 노드마다 캐시: `reachHero = chartRepo.reach(setId, seq, heroPos)` (Float32Array), `mass = Σ reachHero / 1326`, `mixedMass` (3.4), `category` (3.2). 풀은 `openTrainer` 시 만들고, `next()` 마다 `listSets()` 의 `content_hash` 집합이 바뀌었는지 보고 바뀌었으면 재구성 (시드 재임포트 대응).

### 5.2 가중치 (DESIGN 6.3 `w1×w2×w3×w4` 의 v1 구체화)
```
w1(node) = mass                                   실전빈도: 랜덤 핸드가 이 노드에 도달할 확률 (HU 시드는 두 노드 다 1)
w2(node) = 1 + 0.5 · mixedMass                    난이도: 혼합 질량
w4(node) = 1 + min(2, meanEvLoss30d(category) / 0.3)   리크보정 (기록 없으면 1)
w3       = SRS (5.3) 가 대신한다 — 가중치가 아니라 삽입
P(node) ∝ w1·w2·w4
P(c | node) ∝ reachHero[c]                        (P2 3.4: reach_hero 만 쓴다. 상대 카드 제거 없음)
```
상수는 고정이고 테스트는 상수의 현명함이 아니라 **비례 관계**를 검사한다.

### 5.3 SRS 삽입 (SM-2 변형)
`next()` 순서:
1. **leech** (`lapses ≥ 3`, 필터 내, 해시가 풀에 존재, `due_at ≤ now`) 가 있으면 가장 오래된 것.
2. 아니면 `due_at ≤ now` 인 스팟이 있고 `rng() < 0.5` 이면 가장 오래된 due.
3. 아니면 5.2 로 새로 뽑는다. 이미 이 세션에서 낸 키는 다시 내지 않는다 (200회 재시도 후 포기하고 허용).
같은 세션에서 `pending_key` 가 있으면 그것을 그대로 돌려준다 (새로고침 안전). 뽑기의 모든 난수는 세션 `seed` 의 `createRng` 에서 나오고, 상태(DB)가 같으면 **키 열이 결정적**이다.

**문항별 rng 시드 (R2, P3 R1 MAJOR 2)**: 문항 `index` 마다 `createRng(mix(seed, index))` 로 새 rng 를 만드는 방식은 허용하되, `mix` 는 **seed 를 먼저 비선형으로 섞은 뒤 index 와 결합하고 다시 섞어야** 한다. `(seed ^ C) ^ index` 처럼 XOR 만 앞에 두면 `mix(s, i) = mix(s ^ i, 0)` 이 되어 인접 시드 세션이 같은 스팟 집합을 뽑는다 (R1 실측: 시드 5000/5001 의 50문항 집합 교집합 46). 테스트: 시드 `s`·`s+1` (`s ∈ {1, 2, 5000}`) 50문항 스팟 **집합** 교집합 ≤ 5, "같은 시드 → 같은 열" 유지.

SM-2 갱신 (`applyReview(state | null, verdict, now)`):
```
q = Perfect 5 | Minor 3 | Mistake 1 | Blunder 0 | InStrategy 4 | OffStrategy 1
초기: ease 2.5, interval 0, reps 0, lapses 0
if q < 3:  reps = 0; interval = 1; lapses += 1
else:      reps += 1; interval = reps == 1 ? 1 : reps == 2 ? 6 : Math.round(interval · ease)
interval = min(interval, 365)                                        (R2: 상한. 아래)
ease = max(1.3, ease + 0.1 − (5 − q)·(0.08 + (5 − q)·0.02))       (q 적용 순서: interval 계산 → ease 갱신)
due_at = now + interval · 86_400_000
```
**간격 상한 365일 (R2, P3 R1 MAJOR 1)**: 상한이 없으면 Perfect ×16 에 interval 1.2e8 일, `due_at` 1.04e16 > 2^53 이 되어 `node:sqlite` 가 `srs_state` 행을 **읽을 때 throw** 하고 (`ERR_OUT_OF_RANGE`), `answer` 가 500 → pending 이 남아 세션이 영구 정지한다. 트레이너의 목적상 1년에 한 번은 다시 보는 것이 맞으므로 365 로 막는다. `ease` 상한은 두지 않는다 (interval 이 막히면 폭주하지 않는다). 이미 저장된 비정상 행이 있어도 죽지 않도록 `getSrs`/`dueSpots`/`leechSpots` 는 `due_at` 을 `MIN(due_at, <now + 365일>)` 로 읽거나 BigInt 로 읽어 변환한다. 테스트: Perfect ×100 → `dueAt ≤ Number.MAX_SAFE_INTEGER`, `interval ≤ 365`, 파일 DB 왕복이 던지지 않음.

검증값 (테스트): q 열 `[5,5,5]` → interval `1, 6, 16` (ease 2.6 → 2.7 → 2.8, `round(6×2.7)=16`); 이어서 `0` → interval 1, lapses 1, ease `max(1.3, 2.8+0.1−5·0.18) = 2.0`. `[0,0,0]` → lapses 3 = leech.

## 6. 리포트 (`report({ days } | { sessionId })`)
```ts
export interface Report {
  scope: { days: number } | { sessionId: number; durationMs: number };
  totals: Agg;
  byCategory: (Agg & { category: Category })[];
  bySet: (Agg & { contentHash: string; name: string | null })[];
  leaks: { category: Category; meanEvLossBb: number; attempts: number }[];   // ev 채점 attempts ≥ 20 이고 mean ≥ 0.10bb, mean 내림차순
  srs: { due: number; leeches: number };
}
interface Agg {
  attempts: number;                 // 전체 (두 채점 체계 합)
  evGraded: number;                 // graded_by='ev' 개수 — 아래 세 값의 분모
  meanEvLossBb: number | null;      // evGraded 0 이면 null
  bb100: number | null;             // meanEvLossBb × 100
  byVerdict: Record<Verdict, number>;   // 6개 키 전부 (0 포함)
  mixedShare: number | null;        // 혼합 스팟 비율
}
```
`bb/100` = "이 스팟 100개를 실전에서 이렇게 플레이했을 때의 손실" 로 UI 에 설명 한 줄. `InStrategy`/`OffStrategy` 는 개수만 — EV 평균에 절대 들어가지 않는다 (테스트).
