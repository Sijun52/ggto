## 0. 범위와 비범위

**만드는 것**: 카드/콤보/핸드클래스, 레인지(파서·포매터·연산), 핸드 평가기, 에퀴티, 보드 슈트 동형 정규화, 액션 시퀀스 문자열, 프리플랍 상태 기계. 전부 순수 함수. **UI, DB, HTTP, 파일 I/O, 솔버 호출 없음.** 런타임 의존성 0개.

**만들지 않는 것**: 서버, 프론트, SQLite, 솔버 래핑, 트레이너. 169 인덱스를 입력으로 받아 계산하는 함수 (설계 위반).

## 2. 공통 규약

- 성능 경로의 1326 배열은 `Float32Array` / `Uint8Array` / `Uint16Array`. `number[]` 금지.
- `any` 금지. 외부 입력(문자열) 파서는 실패 시 **throw** (`RangeSyntaxError`, `ActionSyntaxError`, `CardSyntaxError` 등 이름 있는 Error 서브클래스). 조용히 빈 결과를 돌려주지 않는다.
- 불변 함수: 입력 배열을 변경하지 않고 새 배열 반환. 예외는 이름에 `InPlace` 를 붙인다.
- 테스트는 **외부에서 알 수 있는 정답**(이 문서의 수치, 수학적 불변식, 왕복 항등)과 대조한다. 구현을 복사한 기댓값은 무효.

## 3. 표현 규약 (전부 고정, 재량 없음)

### 3.1 Card
- `type Card = number` (0..51). **rank = card >> 2 (0=2 … 12=A), suit = card & 3 (0=c, 1=d, 2=h, 3=s)**.
- 문자열: 랭크 `23456789TJQKA` + 슈트 `cdhs`. `"As"` = 12*4+3 = 51, `"2c"` = 0.
- `parseCard(s: string): Card` — 정확히 2글자, 대문자 랭크/소문자 슈트만. 아니면 throw.
- `formatCard(c: Card): string`, `parseCards(s: string): Card[]` (`"KsQh2d"` 붙여 쓴 형태, 중복 카드면 throw), `formatCards(cs)`.
- 상수: `RANKS = "23456789TJQKA"`, `SUITS = "cdhs"`, `cardRank(c)`, `cardSuit(c)`, `makeCard(rank, suit)`.

### 3.2 Combo (1326)
- `type ComboIndex = number` (0..1325). 두 카드 `hi > lo` (카드 id 기준) 에 대해 **`comboIndex(hi, lo) = hi*(hi-1)/2 + lo`**. 인수 순서 무관하게 받아도 되지만 내부 정규화는 이 식.
- `comboCards(i: ComboIndex): [hi: Card, lo: Card]` 역함수.
- `COMBO_COUNT = 1326`.
- `comboContainsAny(i, cards: readonly Card[]): boolean`.

### 3.3 HandClass (169) — 표시 전용
- `type HandClassIndex = number` (0..168). **13×13 격자, row·col 모두 0=A … 12=2. `index = row*13 + col`.**
  - `row === col` → 포켓페어 (AA=0, KK=14, …, 22=168)
  - `row < col` → **수티드** (우상단). 높은 랭크가 row. AKs = 0*13+1 = 1.
  - `row > col` → **오프수트** (좌하단). 높은 랭크가 col. AKo = 1*13+0 = 13.
- `handClassOf(i: ComboIndex): HandClassIndex`, `handClassName(h): string` (`"AA"`, `"AKs"`, `"AKo"`), `parseHandClass("AKs"): HandClassIndex`, `handClassCombos(h): ComboIndex[]` (페어 6, 수티드 4, 오프수트 12).
- `HAND_CLASS_COUNT = 169`.

### 3.4 Range
```ts
type Range = Float32Array;           // length 1326, 각 원소 0..1 (콤보 가중치)
```
- `emptyRange()`, `fullRange()`, `cloneRange(r)`, `rangeFromCombos(entries: Iterable<[ComboIndex, number]>)`.
- `removeBoard(r, board: readonly Card[]): Range` — 보드 카드를 포함하는 콤보 가중치를 0으로.
- `totalWeight(r): number`, `comboCount(r): number` (weight>0 개수).
- `normalize(r): Range` — 합이 1이 되도록. 합이 0이면 `EmptyRangeError` throw.
- `intersect(a, b): Range` — 원소별 곱. `scale(r, k)`.
- `toHandClassView(r): { weight: Float32Array(169); count: Uint8Array(169) }` — 클래스별 가중치 합과 weight>0 콤보 수. **이건 표시용 집계이며 여기서 나온 169 값을 다시 계산에 쓰는 함수는 만들지 않는다.**
- `permuteRangeSuits(r, perm: SuitPerm): Range` (3.6 참조).

### 3.5 레인지 텍스트 문법 (PioSOLVER 호환 부분집합)
```
range    := item ( ',' item )*            (공백은 ',' 전후에서 무시)
item     := spec ( ':' weight )?           weight: 0..1 소수 ('0.5', '1', '.25' 허용)
spec     := pair | pair '+' | pair '-' pair
          | XY sfx? | XY sfx? '+' | XY sfx? '-' XZ sfx?    (X>Y 랭크, sfx ∈ {s,o}, 없으면 s와 o 둘 다)
          | combo                           ('AhKh' 특정 콤보)
```
의미:
- `22+` = 22..AA. `AA+` = AA (허용). `TT-66` 또는 `66-TT` 둘 다 = 66,77,88,99,TT.
- `A2s+` = A2s..AKs (키커를 하이카드 바로 아래까지). `KTo+` = KTo,KJo,KQo. `QT+` = QTs,QTo,QJs,QJo. `T8s+` = T8s,T9s.
- **커넥터 `+` 는 에러** (R1): `XY sfx? '+'` 에서 Y 가 X 바로 아래 랭크이면 (`T9s+`, `76o+`, `32+`, **`AKs+`/`AKo+`/`AK+` 포함**) `RangeSyntaxError`. 이유: 이 표기는 도구마다 뜻이 다르다 (PokerStove/Equilab 계열은 `T9s+` = T9s,JTs,QJs,KQs 커넥터 런; 키커 규칙으로는 T9s 하나 = no-op). 어느 쪽이든 조용히 고르면 한쪽 사용자에게 틀린 레인지가 된다. 커넥터 런은 명시적으로 나열한다 (`T9s,JTs,QJs,KQs`). 에러 메시지에 이 안내를 넣어라.
- `AJs-A9s` = A9s,ATs,AJs. 양 끝 하이카드와 sfx가 다르면 throw (`AJs-K9s`, `AJs-A9o` 는 에러).
- 같은 콤보가 여러 item에 걸리면 **마지막 item 이 이긴다** (덮어쓰기). 따라서 `22+,AA:0` = 22..KK. 문서화하고 테스트하라.
- 빈 문자열(공백만 있는 것 포함)은 빈 레인지다 (`formatRange(emptyRange()) === ""` 왕복 때문). `,` `,,` `AA,` 같은 빈 item 은 에러.
- 잘못된 입력은 전부 throw: `2s+`, `AKx`, `AA:1.5`, `AA:-1`, `A2s-`, `,`, `A K`, 소문자 랭크 `aa`, `T9s+`, `AKs+`.
- 랭크 문자에서 `T` 만 10이다. `10` 은 에러.
- 가중치 표기는 파서가 관대하다 (`AA:1.0`, `AA:.5`, `AA:01` 허용, 전부 값으로만 해석). 정규형은 포매터가 정한다 (아래).

`parseRange(text): Range`, `formatRange(r): string`.
**포매터 정규형**: 클래스 가중치가 클래스 내 전 콤보에서 동일하면 클래스 표기, 아니면 콤보 표기. 클래스는 페어 내림차순 → 수티드(하이카드 내림, 키커 내림) → 오프수트 순. 연속 동일 가중치 페어/키커 런은 `+`/`-` 로 압축(런 길이 ≥ 2 일 때만, 최고까지 닿으면 `+`, 아니면 높은 쪽 먼저 `X-Y`: 페어 `TT-66`, 키커 `AJs-A9s`). 커넥터 런은 `+` 를 쓰지 않는다 (`AKs` 는 `AKs`, 3.5 규칙과 일관). 가중치 1은 생략, 아니면 `:w` (w는 최대 소수 4자리, 후행 0 제거; 4자리 반올림이 0이 되는 콤보는 출력하지 않는다). **왕복 조건**: 모든 Range r 에 대해 `parseRange(formatRange(r))` 의 각 원소가 r과 `|Δ| ≤ 1e-4`. 그리고 정규 텍스트 t 에 대해 `formatRange(parseRange(t)) === t`.

### 3.6 SuitPerm
`type SuitPerm = readonly [number, number, number, number]` — `perm[s]` = 원본 슈트 s 가 가는 슈트. `IDENTITY_PERM`, `invertPerm`, `applyPermToCard(c, perm)`, `ALL_SUIT_PERMS` (24개).

## 4. 모듈별 요구사항과 테스트

### 4.1 card / combo / handClass
필수 테스트:
- `parseCard`/`formatCard` 52장 왕복. `"As"`→51, `"2c"`→0, `"Td"`→33.
- `comboIndex`/`comboCards` 가 0..1325 전단사: 1326개 전부 왕복, 중복 없음, 범위 내.
- `handClassOf` 로 1326 콤보를 169 클래스에 분배하면 클래스당 콤보 수가 페어 6 / 수티드 4 / 오프수트 12 이고 합 1326 (13×6 + 78×4 + 78×12).
- `handClassName(0)==="AA"`, `(1)==="AKs"`, `(13)==="AKo"`, `(168)==="22"`, `(12)==="A2s"`, `(156)==="A2o"`. 169개 이름 전부 `parseHandClass` 왕복.

### 4.2 range (연산)
- `removeBoard(parseRange("AA"), parseCards("As"))` → weight>0 콤보 정확히 3개 (AhAd, AhAc, AdAc), 그리고 `normalize` 후 각 1/3.
- `removeBoard(fullRange(), 플랍 3장)` → comboCount = C(49,2) = 1176.
- `normalize(removeBoard(parseRange("AsKs"), ["As"]))` → `EmptyRangeError`.
- **정규화는 카드 제거 후에** 한다는 것을 API 사용 예제 테스트로 고정: 제거→정규화 결과 합 = 1.
- `toHandClassView(fullRange())` count 가 4.1의 분포와 같다.

### 4.3 range (파서/포매터)
- 전개 테스트 (콤보 수): `"22+"` → 78, `"A2s+"` → 48, `"KTo+"` → 36, `"AJs-A9s"` → 12, `"QQ:0.5"` → 6개 각 0.5, `"QT+"` → 32 (QTs 4 + QTo 12 + QJs 4 + QJo 12), `"AA+"` → 6, `"TT-66"` = `"66-TT"` → 30, `"AhKh"` → 1, `"AhKh:0.3,AKs"` → AhKh 가중치 1 (마지막이 이김), `"AKs,AhKh:0.3"` → AhKh 0.3, 나머지 3개 1.
- 표준 6max 오픈 레인지 하나 (예: `"22+,A2s+,K5s+,Q8s+,J8s+,T8s+,97s+,86s+,75s+,65s,A9o+,KTo+,QTo+,JTo"`) 의 콤보 수를 **손으로 센 값**과 대조하고 계산 과정을 테스트 주석에 적어라.
- 에러 케이스 전부 throw 확인 (3.5 목록). **커넥터 `+`**: `"T9s+"`, `"76o+"`, `"32+"`, `"AKs+"` 네 가지 전부 `RangeSyntaxError`; 원갭 `"T8s+"` 는 8콤보로 정상.
- 왕복: 무작위 Range 200개(시드 고정, 가중치 {0, 0.25, 0.5, 1} 에서 클래스 단위/콤보 단위 혼합) 에 대해 `parse(format(r)) ≈ r` (1e-4). 정규 문자열 20개에 대해 `format(parse(t)) === t`.

### 4.4 evaluator
```ts
type HandValue = number;   // 클수록 강함. 카테고리는 handCategory(v) 로 복원
enum HandCategory { HighCard=0, Pair, TwoPair, Trips, Straight, Flush, FullHouse, Quads, StraightFlush }
evaluate5(cards: readonly Card[]): HandValue     // 정확히 5장
evaluate7(cards: readonly Card[]): HandValue     // 5..7장 (베스트 5)
handCategory(v: HandValue): HandCategory
```
- `evaluate5/evaluate7` 는 카드 범위(0..51)와 **중복 카드**를 검사한다 (`CardSyntaxError`) (R1 권장 → R2 구현 확정). 핫 경로는 `evaluateMasks` (`@ggto/core/internal`, 검증 없음) 이고 에퀴티 모듈은 그것을 직접 쓴다. R2 실측: `evaluate7` ×200k 23ms → 30ms (편의 API 만 영향), exact/hvh/MC 핫 경로 변화 없음.

필수 테스트:
- 카테고리 예제 10개 (로열, 스틸휠, 쿼드, 풀하우스, 플러시, 휠, 트립스, 투페어, 원페어, 하이카드) — 각각 정확한 카테고리.
- 순위: 휠(A2345) < 6-high 스트레이트; 스틸휠 < 6-high 스트레이트플러시; `AAAKK > KKKAA`; `AAKK2 > AAQQK`; 플러시 킥커 비교 `AKQJ9s > AKQJ8s`; 7장에서 베스트 5 선택 (예: 두 페어 셋에서 상위 2개 + 킥커).
- **5장 전수 분포** (2,598,960 핸드): `[HighCard 1302540, Pair 1098240, TwoPair 123552, Trips 54912, Straight 10200, Flush 5108, FullHouse 3744, Quads 624, StraightFlush 40]`. 이건 `npm test` 에 포함 (내 나이브 구현으로 ~10s; 그보다 느리면 최적화).
- `test/slow/`: **7장 전수 분포** (133,784,560): `[23294460, 58627800, 31433400, 6461620, 6180020, 4047644, 3473184, 224848, 41584]`.
- 동일 값 → 동일 HandValue (tie): `AhKh QhJhTh 2c3d` vs `AsKs QsJsTs 2c3d` 같은 값.

### 4.5 equity
```ts
interface EquityResult { win: number; tie: number; lose: number; equity: number }   // equity = (win + tie/2) / total
equityHandVsHand(hero: [Card,Card], villain: [Card,Card], board: readonly Card[]): EquityResult   // 전수. board 0..5장
interface RangeEquityOptions { mode: 'exact' | 'monte-carlo'; samples?: number; seed?: number }
interface RangeEquityResult {
  hero: number;                 // 히어로 **에퀴티** = 유효 쌍에 대한 (win + tie/2) 의 가중 집계. (R1 정본)
  villain: number;              // 빌런 에퀴티. 불변식 hero + villain = 1
  tie: number;                  // 타이 빈도 (가중). 불변식 heroWin + villainWin + tie = 1
  heroWin: number;              // 순수 승률 = hero − tie/2   (R1 추가)
  villainWin: number;           // = villain − tie/2
  heroPerCombo: Float32Array;   // 1326: 각 히어로 콤보의 에퀴티 (레인지 밖/보드 충돌은 NaN)
  villainPerCombo: Float32Array;
  matchups: number;             // 유효 콤보 쌍 수 (양쪽 weight>0, 보드/서로 카드 충돌 없음)
}
equityRangeVsRange(hero: Range, villain: Range, board: readonly Card[], opts: RangeEquityOptions): RangeEquityResult
```
규칙:
- 보드 카드와 겹치거나 서로 겹치는 콤보 쌍은 제외. 가중치는 두 레인지 가중치의 곱. `heroPerCombo[i]` = 콤보 i 와 유효한 빌런 콤보들의 hand-vs-hand 에퀴티를 빌런 가중치로 평균한 값.
- `exact` 는 보드 3..5장에서 필수 지원. 구현 힌트: 런아웃마다 1326 콤보를 한 번씩 평가해 정렬하고 누적합으로 O(n log n) 처리. 1326×1326 쌍마다 평가하지 마라.
- 보드 0~2장 `exact` range-vs-range 는 throw (`UnsupportedError`) — 프리플랍 1.7M × 1326, 보드 1~2장도 같은 자릿수라 TS 로 안 된다. hand-vs-hand 프리플랍 exact 는 허용. (R1: 1~2장 명시)
- `monte-carlo`: `rng.ts` 의 시드 PRNG (xoshiro128** 또는 splitmix 기반, `Math.random` 금지). 동일 seed → 동일 결과. MC 모드의 `heroPerCombo`/`villainPerCombo` 는 **추정치**이며, 한 번도 샘플되지 않은 콤보는 NaN 이다 (레인지 밖과 구분되지 않는다 — P0 소비자 없음, 필요해지면 `samplesPerCombo` 추가). 샘플링 분포는 exact 의 가중 정의와 같아야 한다 (콤보 쌍을 가중치 곱에 비례해 뽑고 충돌 쌍은 거절).

### 4.6 isomorphism
```ts
canonicalBoard(board: readonly Card[]): { board: Card[]; perm: SuitPerm }
   // board 는 3..5장. 결과 board = 원본에 perm 적용 후 카드 id 오름차순 정렬. 24개 순열 결과 중 사전순 최소.
   // 같은 동치류의 모든 보드는 같은 결과 board 를 낸다 (유일성).
suitStabilizer(ranges: readonly Range[], eps = 1e-6): SuitPerm[]
   // 모든 레인지를 불변으로 두는 순열의 부분군. 항등 순열은 항상 포함.
canonicalize(board: readonly Card[], ranges: readonly Range[]): { board: Card[]; ranges: Range[]; perm: SuitPerm }
   // suitStabilizer(ranges) 안에서만 최소 보드 선택. ranges 에도 같은 perm 적용해 반환. 레인지 배열 길이는 1 이상 임의.
```
필수 테스트:
- 플랍 22,100개 전부 `canonicalBoard` → 서로 다른 결과 보드 **1,755개**, 클래스 크기 분포 `{4: 299, 12: 1170, 24: 286}`.
- 턴 270,725개 → **16,432**. (`npm test` 포함, 내 구현 3초.) `test/slow/`: 리버 2,598,960 → **134,459**.
- 역변환: 모든 플랍에 대해 `invertPerm(perm)` 을 결과에 적용하면 원본 집합 복원.
- 예제: `Ks7h2h` 와 `Kd7s2s` 와 `Kc7d2d` 가 같은 정규 보드. `Ks7h2h` 와 `Ks7h2s` 는 다름.
- `suitStabilizer([fullRange()])` 길이 24. `suitStabilizer([parseRange("AsKs")])` 는 스페이드를 고정하는 순열 6개. `suitStabilizer([parseRange("AsKs"), parseRange("AhKh")])` 는 s와 h를 고정 → 2개. `parseRange("AKs")` (4콤보 동일 가중치) → 24개.
- `canonicalize(Kh7d2c, [parseRange("AsKs")])`: 결과 보드에서 원본 스페이드 카드가 없으므로 어떤 perm이든 스페이드가 스페이드로 감을 확인 (`perm[3] === 3`), 반환 range 는 여전히 AsKs 에만 가중치.
- 완전 비대칭 레인지(예: `"AsKs:1,AhKh:0.5,AdKd:0.25,AcKc:0.125"`) → stabilizer 길이 1, `canonicalize` 결과 보드 = 정렬된 원본.
- 정규화 결과에 대한 `equityRangeVsRange(exact, 플랍)` 집계값이 원본과 1e-6 이내 일치 (순열 불변성 — 이게 캐시 공유의 정당성이다).

주의 (R1, P4 설계 메모): 4~5장 보드의 정규형은 **정렬된 집합** 기준이라 플랍/턴/리버의 스트리트 구조를 버린다 (`Ks7h|2h` 와 `Ks2h|7h` 가 같은 결과). 턴/리버 솔브의 캐시 키는 P4 스펙에서 street-aware 정규화(정렬된 플랍, 턴, 리버 튜플의 사전순 최소)를 따로 정의한다. P0 의 함수는 그대로 둔다.

### 4.7 action (액션 시퀀스 문자열 — 캐시 키)
```ts
type Action =
  | { kind: 'fold' } | { kind: 'check' } | { kind: 'call' }
  | { kind: 'bet'; amount: number }        // 이번 스트리트 첫 공격. 금액 = 베팅 총액
  | { kind: 'raise'; amount: number }      // 금액 = raise-TO 총액 (이번 스트리트 누적)
  | { kind: 'allin' };
type Street = Action[];
type ActionSequence = Street[];             // 프리플랍만이면 길이 1

formatActionSequence(seq: ActionSequence): string
parseActionSequence(s: string): ActionSequence
```
문법 (정규형만 허용):
```
sequence := street ( '/' street )*         빈 스트리트 허용 (예: "B33-C/" 는 불허 — 후행 '/' 금지; 진행 중이면 그냥 마지막 스트리트까지만)
street   := action ( '-' action )*
action   := 'F' | 'X' | 'C' | 'A' | 'B' amount | 'R' amount
amount   := 정규 소수: '0' 아닌 정수부(또는 '0'), 소수부는 있으면 후행 0 없이. 예 '2.5' '11' '0.5' '225'.
            '2.50', '02', '.5', '2.' 는 에러. 음수/지수 표기 에러.
```
- 빈 문자열은 빈 시퀀스 `[]` (루트). `format([]) === ""`. 빈 스트리트를 포함하는 시퀀스(`[[]]`, `[[F], []]`)는 문자열로 표현할 수 없으므로 `formatActionSequence` 가 `ActionSyntaxError` 를 던진다 (R1).
- 대소문자 엄격. 공백 불허. 알 수 없는 토큰/빈 토큰(`F--C`, `-F`)은 throw.
- 금액 단위는 문자열이 정하지 않는다 (호출 측 config가 bb 또는 chips 를 정한다). 포매터는 `amount` 를 `String(amount)` 정규형으로 출력하되, 소수부는 최대 2자리로 반올림 (bb 단위 0.01 해상도). 파서가 읽은 값을 다시 포맷하면 동일 문자열이어야 한다.
- **`MAX_AMOUNT = 1e9`** (R2, 공개 상수): `formatAmount`/`parseActionSequence` 는 이 값을 넘는 금액에 `ActionSyntaxError`. 호출 측(UI 검증, P1 서버 입력 검증)은 같은 상수를 쓴다. 근거: 2자리 반올림 `Math.round(x*100)/100` 이 정확하려면 `x*100 < 2^53` (x < 약 9e13) 이어야 하고, 지수 표기는 1e21 부터다 — 1e9 는 그 안에서 bb/chips 어느 단위로도 충분히 큰 값을 고른 것이지 기술적 경계가 아니다 (코드 주석의 "그 위로 가면 지수 표기" 는 부정확, R2 MINOR 3).

필수 테스트:
- 왕복: `"F-F-R2.5-F-F-R11-C"`, `"B33-C/B75-R225-C/X-X"`, `"X-B12.5-R40-A-C"`, `""` 에 대해 `format(parse(s)) === s`.
- 파싱 결과 구조 확인 (예: 첫 문자열 → 1 스트리트 7 액션, 세 번째 액션 `{kind:'raise', amount:2.5}`).
- 비정규 입력 throw: `"F.F.R2.5"`, `"f-f"`, `"R2.50"`, `"R02"`, `"F--C"`, `"-F"`, `"B33-C/"`, `"B"`, `"R"`, `"F C"`.
- 시퀀스 200개를 무작위 생성해 `parse(format(x))` 가 깊은 동등 (금액은 2자리 반올림 후 생성).

### 4.8 preflopState (프리플랍 상태 기계)
```ts
interface PreflopConfig {
  positions: readonly string[];        // 액션 순서. 6max: ["UTG","HJ","CO","BTN","SB","BB"]. 2max: ["SB","BB"] (SB=BTN 먼저)
  blinds: readonly { pos: string; amount: number }[];   // [{pos:"SB",amount:0.5},{pos:"BB",amount:1}]. 스트래들은 항목 추가
  ante: { mode: 'none' } | { mode: 'per_player'; amount: number } | { mode: 'bb_ante'; amount: number };
  stack: number;                       // 유효 스택 (bb). 전원 동일 (P0 범위)
}
interface PreflopState {
  toAct: string | null;                // null = 프리플랍 종료 (전원 폴드 또는 액션 클로즈)
  pot: number;                         // 앤티 + 블라인드 + 모든 투입 합
  contributions: Record<string, number>;   // 포지션별 이번 스트리트 투입 (블라인드 포함)
  folded: ReadonlySet<string>;
  allIn: ReadonlySet<string>;
  currentBet: number;                  // 맞춰야 할 총액
  minRaiseTo: number;                  // 다음 레이즈의 최소 total (마지막 레이즈 증분 규칙)
  playersIn: string[];                 // 폴드 안 한 사람
  actionsTaken: Action[];
  isTerminal: boolean;                 // 전원 폴드(1명 남음) 또는 베팅 라운드 종료
}
preflopState(config: PreflopConfig, seq: Street): PreflopState
legalActions(config, state): Action[]  // fold/call/check/raise(min~allin)/allin 의 목록. 금액은 minRaiseTo 만 넣고 사이즈 후보 열거는 호출 측 몫
```
규칙:
- 첫 액터는 마지막 블라인드/스트래들 다음 포지션 (6max 표준: UTG). 액션은 `positions` 순환.
- BB(또는 마지막 블라인드)가 레이즈 없이 차례를 받으면 `check` 가 합법, `call` 은 불법.
- 레이즈 최소 증분 = 직전 레이즈 증분 (첫 레이즈는 가장 큰 블라인드/스트래들 1개). `stack` 을 넘는 레이즈는 불법.
- **올인 정규형 (R1, 캐시 키 유일성)** — 한 상태에는 문자열이 정확히 하나여야 한다:
  - `R<amount>` 에서 `amount >= stack` 은 **불법** (`IllegalActionError`: "raise to the full stack must be written as A"). 스택 전부를 넣는 공격은 오직 `A`.
  - `A` 는 **레이즈일 때만** 합법 (`stack > currentBet`). 스택이 `currentBet` 이하라서 베팅을 올리지 못하는 올인(콜 올인)은 `A` 가 아니라 `C` 로 쓴다 (`IllegalActionError`: "all-in that does not raise must be written as C").
  - `C` 는 `currentBet >= stack` 이면 스택 전부를 넣고 그 플레이어를 `allIn` 에 넣는다.
  - `A` 의 레이즈 증분이 최소 증분 미만이어도 합법 (올인 예외). `minRaiseTo` 갱신은 `max(stack − currentBet, 직전 증분)`.
  - `legalActions` 는 `allin` 을 `stack > currentBet` 일 때만 넣는다. **어떤 상태에서도 결과 상태가 같은 액션 두 개가 목록에 있으면 안 된다.**
- **키 계약 (R2, 반박 1 판정)** — 액션 문자열이 무엇을 식별하는지:
  - 문자열은 **히스토리(액션 순서)** 를 식별한다. config 가 주어지면 정규 문자열 ↔ 히스토리는 전단사다 (`parse∘format = id`, 액터는 상태 기계가 결정).
  - 한 노드에서 **서로 다른 토큰이 같은 후속 상태**(contributions/allIn/folded/toAct/currentBet/minRaiseTo)를 만들면 안 된다. 이것이 위 올인 정규형 규칙의 목적이며, R2 리뷰어가 HU/3max/6max 소형 스택 트리 전수(13,600 노드, 후보 토큰 전부 시도)로 위반 0 을 확인했다.
  - 서로 다른 히스토리가 같은 포트-상태를 갖는 것(transposition, 예 HU `C-R2-C` vs `R2-C`, 3max `F-C-R2-C` vs `F-R2-C`, `R5-A-C` vs `R2-A-C`)은 **정상이고 결함이 아니다**. 림프-레이즈-콜과 레이즈-콜은 다른 인포셋이고 도달 레인지가 다르다. `pf_node.action_seq` 는 히스토리 키이므로 이들은 서로 다른 행이며, P2/P3/P4 어디서도 포트-상태 기준으로 합치지 않는다. 포트-상태 기준 동일성이 필요한 소비자(예: 포스트플랍 솔브 캐시)는 별도 키(팟, 스택, 레인지 해시)를 쓴다 — P4 스펙 사안.
  - `PreflopState.actionsTaken` 이 히스토리를 담으므로 스냅샷 비교에서 이를 빼면 transposition 이 "중복" 으로 보인다. 테스트는 **한 노드의 후속 상태 비교**에만 그 스냅샷을 쓴다.
- `bet` (`B<amt>`) 은 프리플랍에서 도달 불가다 (블라인드가 최소 1개 필수 → `currentBet > 0`). 구현의 `bet` 분기(풀스택 `B<stack>` 금지 포함)는 포스트플랍 상태 기계(P4)가 상속할 규칙을 선반영한 것이며 P0 테스트로 커버되지 않는다 (R2 반박 3 수용, 주석으로 "프리플랍 도달 불가" 명시).
- config 검증 (R2 MINOR 1, P2 임포터 착수 전까지): 어떤 포지션의 포스트 블라인드 합계가 `stack` 이상이면 `PreflopConfigError`. 지금은 `stack: 0.5, BB 1` 같은 config 에서 `legalActions` 가 `[F]` 만 주는데 `C` 가 성공하는 등 계약이 깨진다 (실사용 config 에서는 발생하지 않음).
- 폴드/올인한 사람은 건너뛴다. 남은 1명이면 terminal. 모두 콜/체크로 마지막 공격에 응답하면 terminal.
- 시퀀스가 불법 액션을 포함하면 `IllegalActionError` (몇 번째 액션, 누구, 왜).

필수 테스트 (6max 100bb, SB 0.5 / BB 1):
- `""` → toAct "UTG", pot 1.5, currentBet 1, minRaiseTo 2.
- `"F-F-R2.5-F-F-R11-C"` → 액션 순서 UTG,HJ,CO,BTN,SB,BB,CO. terminal, playersIn [CO, BB], pot 22.5 (SB 0.5 + BB 11 + CO 11), contributions {CO:11, BB:11, SB:0.5}.
- `"F-F-F-F-F"` → terminal, playersIn [BB], toAct null (BB 워크).
- `"F-F-F-F-C"` → toAct "BB", legalActions 에 check 포함, call 미포함. 이어서 `-X` → terminal, pot 2.
- `"F-F-F-R3-R10-R22"` (R1: F 3개로 오타 수정) → 액터 순서 UTG F, HJ F, CO F, BTN R3, SB R10, BB R22 → toAct **BTN**, currentBet 22, minRaiseTo 34 (마지막 증분 22−10 = 12), contributions {BTN:3, SB:10, BB:22}.
- `"F-F-F-F-R3-R10-R22"` (F 4개) → SB R3, BB R10, SB R22 → toAct **BB**, contributions {SB:22, BB:10}.
- 불법: `"C"` 다음 `"X"` by HJ (currentBet 존재 시 체크 불가) → IllegalActionError. `"R1.5"` (최소 2 미만) → 에러. `"R101"` → 에러. `"F-F-F-F-F-C"` (종료 후 액션) → 에러. `"F-F-F-F-C-C"` (콜할 것 없음) → 에러.
- 올인 정규형 (R1): `"R100"` → IllegalActionError. `"A"` → UTG allIn, currentBet 100, toAct HJ, `legalActions` 의 kind 가 정확히 `[fold, call]` (allin 없음). `"A-A"` → IllegalActionError (HJ 는 `C`). `"A-C"` → HJ 도 `allIn`, pot 201.5. `"R99.5"` 뒤 `legalActions` = `[fold, call, allin]` (0.5 만큼 레이즈이므로 allin 합법), `"R99.5-A"` 합법, currentBet 100. 무작위 합법 시퀀스 2,000개에서 `legalActions` 각 원소를 적용한 결과 상태 스냅샷(JSON)이 서로 다름.
- 2max `["SB","BB"]`: `""` → toAct SB. `"R2.5-C"` → terminal, pot 5.
- 스트래들: blinds 에 `{pos:"UTG", amount:2}` 추가 시 첫 액터 HJ, currentBet 2, minRaiseTo 4.
- 앤티 `bb_ante 1`: pot 시작 2.5. `per_player 0.1` (6인): 2.1.
