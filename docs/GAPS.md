# 기능 공백 — 사용자 지적 (2026-09-17)

> "각 기능은 **토너먼트와 캐시게임을 분리**해서 만들어주고,
> **Range 도 포지션별로 어떤 상황에 어떤 핸드레인지를 써야 하는지**의 기능이 필요함.
> **트레이너나 차트도 푸시폴드밖에 없고**"

세 지적 모두 타당하다. 그리고 **뿌리는 하나다.**

> ## 범위 확정 (2026-09-17) — **토너먼트(MTT) 전용**
>
> 사용자 결정: **캐시게임을 범위에서 뺀다.** 비용 절감이 이유다.
>
> **빠지는 것**: 아래 P9(캐시 딥스택 중첩 솔브) 전체. 게임 타입 탭도 불필요해진다.
> **남는 것**: `chart_set.game_type` 컬럼은 유지한다 (제거 비용 > 유지 비용, 나중 확장 여지).
> 값은 `'mtt'` 만 쓴다.
>
> **이 결정이 오히려 정확도에 유리하다.** MTT 숏스택(≤20bb)은 액션이 사실상
> 푸시/폴드·림프·3bet-jam 으로 수렴해 **핸드가 프리플랍에서 끝난다.**
> 그래서 올인 에퀴티가 거의 정확하고, HU 푸시/폴드와 **같은 exploitability 게이트**를
> 걸 수 있다. 포스트플랍 근사 모델의 오차를 떠안지 않아도 된다 —
> P9 가 안고 있던 "근사인데 정확한 척" 리스크가 사라진다.

| 계층 | 상태 | 근거 |
|---|---|---|

| **게임 타입 UI** | ❌ 없음 | 데이터엔 `game_type` 이 있는데 화면에 필터·구분이 없다 |

**결론**: 데이터 모델과 도메인 로직은 이미 6-max·MTT 를 표현할 수 있다.
차트가 HU 푸시/폴드 6개뿐이라 그 위의 모든 기능이 거기 갇혀 있었다 — **P7 이 그 병목을 푼다**
(생성기·에퀴티 표·은퇴/마이그레이션). 남은 것은 UI(P8): 360 셋을 고를 수 있는 필터와
`limitations` 표기다.

## 왜 6-max 프리플랍이 HU 푸시/폴드보다 훨씬 어려운가

정직하게 적는다. 이게 일정의 대부분을 결정한다.

**HU 푸시/폴드가 쉬운 이유**: 모든 액션이 올인 아니면 폴드라 **핸드가 프리플랍에서 끝난다.**
그래서 169×169 에퀴티 표 하나로 정확한 페이오프를 계산할 수 있고, 포스트플랍 모델이 아예 필요 없다.
우리 시드 차트가 HoldemResources Nash 표와 2,007/2,010 일치하는 것도 이 때문이다.

**6-max 가 어려운 이유**:
1. **멀티웨이** — 3명 이상이 남는 팟. 에퀴티가 쌍별이 아니라 다자간이 된다
2. **딥스택이면 포스트플랍이 남는다** — `R2.5` 로 열고 콜받으면 핸드가 계속된다.
   그 노드의 EV 는 "올인 에퀴티" 가 아니라 **포스트플랍 플레이의 가치**다.
   이걸 올인 에퀴티로 근사하면 딥스택에서 틀린 차트가 나온다 (그게 트레이너로 들어가면 틀린 걸 외운다)
3. **트리 크기** — 6 포지션 × 여러 레이즈 사이즈 × 멀티웨이 → 인포셋 수백만

### 그래서 나누면

| 구간 | 포스트플랍 필요? | 난이도 | 비고 |
|---|---|---|---|
| **MTT 숏스택 (≤ 20bb) · 2~9-max** | 거의 불필요 | **중** | 푸시/폴드 + 림프 + 3bet-jam 이 지배적. 올인 에퀴티가 거의 정확하다. **앤티·BB앤티 모델링이 핵심** |
| **MTT 미들 (20~40bb)** | 부분적 | 중상 | 리레이즈-폴드 라인이 생긴다 |
| **캐시 딥스택 (100bb)** | **필수** | **상** | 포스트플랍 모델 없이는 정확한 RFI/3bet 차트가 안 나온다. P4 솔버를 리프에서 호출하는 중첩 솔브가 필요하고 매우 비싸다 |
| **ICM (MTT 페이아웃)** | — | 상 | 버블·파이널테이블에서는 칩 EV 가 아니라 ICM EV 다. 별도 서브시스템 |

## 계획

### P7 — 프리플랍 생성기 확장 (병목 해소) — 정본은 `docs/specs/P7.md`

**목표 테이블 사이즈: 9-max 까지.** MTT 는 9-max 로 시작해 사람이 터질수록 줄어든다 —
9·8·7·6·5·4·3·2 **사다리 전체**가 실전이다.

- **모델 `pf-nmax-v1` = 푸시/폴드뿐** (D30): 잼 없으면 `{F,A}`, 잼 마주하면 `{F,C}`, 각자 한 번 행동.
  림프·미니레이즈는 **P7 에 없다** — 어느 쪽으로 넣어도 (플랫콜 허용 → 포스트플랍 EV 필요 / 금지 → 레이즈-폴드 과대평가)
  게이트가 "모델 안에서만" 정확해진다. **P7b** 로 분리하고, 측정된 포스트플랍 EV 모델 없이는 넣지 않는다.
- **테이블 사이즈 2~9** × **앤티 3종** (`none` / `bba1` = BB 앤티 1bb, 온라인 표준 / `pp0.125` = 전원 앤티) × **스택 15단** (3~15, 17, 20)
  = **360 차트**, 전부 `game_type='mtt'`. 포지션 이름은 `tablePositions(n)` (`UTG UTG1 UTG2 LJ HJ CO BTN SB BB`, `+` 금지, D37).
  스택 = 앤티 납부 후·블라인드 포함 인핸드, 전원 동일 (D36).
- **멀티웨이 올인** — 진짜 비용은 여기였고, 직접 재서 결정했다 (D31·D32):
  - 3-way 클래스 표 818,805 트리플. **전수는 ≈ 1,100 코어시간이라 불가** → **MC S=100,000/트리플** (6 워커 ≈ 2.5h, SE ≤ 0.16%p, 6.55MB u16 커밋). 정확 정답 7개로 게이트.
  - **콜러 상한 2 (3-way 쇼다운)**. 4-way 클래스 표는 34.8M 항목이라 불가. 상한이 만드는 편차를 `truncationGainBb` 로 **측정해 파일에 적고**, 0.02bb 초과 차트는 출하하지 않는다. HRC 기본 모드도 "최대 3명 활성" 이다.
  - 폴더의 카드 제거는 활성 핸드 기준만 (보수 규칙), **번칭 없음** (D33) — HRC 기본 모드와 같은 가정. 한계로 표기.
- **정확도 게이트** (D34): `epsilonBb = max_i (BR 이득) < 0.005bb` — 모델 안 ε-균형. `nashConv/n` 도 기록. n≥3 은 CFR 수렴 무보장이라 **게이트는 측정**이고 실패 차트는 미출하.
  추가 게이트: HU 회귀 (새 솔버 n=2 ≡ 기존 `pushFold.ts`, P2 13절 기준), 서브게임 동형 (none/bba1 에서 "k 폴드 뒤" ≡ (n−k)-max 루트 — 2인 서브게임 hard), 단조성(포지션·스택·앤티), Σ_i u_i = 0.
- **공개 기준값**: 9-max 푸시/폴드 Nash 의 출처 있는 공개 표는 **없다** (HRC 무료 계산기는 HU 뿐, 나머지는 출처·모델 불명 이미지 차트). 서브게임 동형 덕에 HU(HRC 2007 대조 완료) 가 모든 n 의 SB-vs-BB 노드를 고정하고, pokercoaching 의 9-handed 10bb 순수화 차트(HJ 20.1% / BTN 33.0% / SB 60.5%) 는 sanity 로만 쓴다. 3인 이상은 리뷰어의 **독립 솔버(감쇠 fictitious play)** 교차검증.
- **기존 것**: 옛 HU 6개는 새 `2-max (HU)` 로 대체되고 해시가 바뀐다 → `aliases.json` + `chart-import --aliases`(은퇴) + **명시적 `npm run trainer:migrate`** (백업 후 치환, D35). `seed` 는 2-max 45 차트 (1분 안), **`gen:charts`** 가 전체 사다리 (6 워커 ≤ 6h, 재개 가능).
- **ICM 없음** — 칩 EV. 차트의 `source.params.limitations` 다섯 문장이 P8 UI 에 그대로 뜬다.

#### 9-max 의 비용이 어디서 오나 (직접 잰 값)
| 축 | 값 | 영향 |
|---|---|---|
| 트리 (콜러 상한 2) | 9-max 결정 128 · 2-way 36 · 3-way 84 · 절단 결정 126 | 반복당 3-way 축약 252회 × 169³ + 폴더 행렬 128회 ≈ 1.8 GFMA (조밀) → 희소화 뒤 10~50배 감소 |
| 3-way 표 | 818,805 트리플 × 100k 샘플 | 1회 2.5h, 커밋. 2-way 는 여전히 전수 |
| 차트 수 | 360 | 9-max 차트 ≤ 10분 예산, 사다리 전체 ≤ 6h (6 워커). DB ≤ 200MB, 노드 ≈ 16,470 |
| 절단 | 4-way+ 터미널 382개 제거 (9-max) | `truncationGainBb` 측정. 9-max ≤ 5bb 앤티 차트가 상한(0.02bb) 근처일 수 있다 — 실측이 답 |

**핵심**: 9-max 의 비용은 **선형 + 표 1회**다. 캐시 딥스택은 포스트플랍 모델이 필요해 **차원이 다른** 비용이었다. 그래서 9-max 는 되고 캐시는 안 된다.

#### P7b (미정, P8 뒤) — 액션 확장·번칭
림프·미니레이즈·3bet-jam 을 넣으려면 플랫콜 뒤 팟의 EV 모델이 필요하다. 후보: "체크다운(올인 에퀴티) 근사" 를 P4 솔버로 표본 플랍에서 **측정**해 오차를 적는 것. 오차를 못 재면 넣지 않는다. 번칭(폴드 레인지 카드 제거) 도 같은 페이즈 후보.

### P8 — 게임 타입 분리 + 레인지 브라우저
- ~~cash / MTT 탭~~ — MTT 전용이라 **불필요**. 대신 **스택 구간 · 테이블 사이즈 · 앤티 형태**로 고른다
  (MTT 에서 실제로 갈리는 축은 게임 타입이 아니라 이 셋이다)
- **Range 페이지 재설계**: 자유 텍스트 입력은 남기되,
  주 기능을 **포지션 × 상황 브라우저**로 — "BTN · vs CO open · 3bet 레인지"
  를 고르면 격자가 뜨고, 옆에 "왜" (EV·빈도·대안)
- 트레이너 카테고리를 게임 타입별로 분리. 리포트도 분리
- 기존 `chart-gen` 출처 기록(`source`) 은 그대로

### ~~P9 — 캐시 딥스택 차트~~ — **취소됨 (MTT 전용 결정)**

아래는 기록용. 캐시게임을 다시 넣게 되면 여기서 시작한다.
- 프리플랍 트리의 리프에서 P4 포스트플랍 솔버를 호출하는 중첩 솔브
- 또는 포스트플랍 EV 근사 모델 + 그 근사의 오차를 측정해 명시
- **이건 정확도 주장을 조심해야 한다.** 근사면 근사라고 `source` 에 적는다

### 순서를 이렇게 잡은 이유
P7 이 끝나면 **MTT 는 바로 쓸 수 있게 된다** (숏스택이 MTT 의 실전 대부분이다).
P8 이 끝나면 앱이 "포지션별로 뭘 해야 하나" 라는 원래 질문에 답한다.
P9 는 캐시 딥스택을 위한 것이고 가장 비싸므로 마지막이다.

**P6(포스트플랍 트레이너)보다 P7·P8 이 먼저다** — 프리플랍이 실전 빈도가 훨씬 높고,
지금 앱이 "푸시폴드 전용" 으로 보이는 원인이 여기이기 때문이다.
